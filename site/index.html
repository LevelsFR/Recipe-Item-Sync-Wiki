Recipe Item Sync v3

Make server-side datapack items visible in recipe viewers.

Recipe Item Sync discovers supported virtual ItemStacks and recipe data on the server, then synchronizes them to NeoForge clients so players can find them in JEI, REI, or EMI before crafting or receiving the item.

Get started View source
The datapack can stay server-side. Clients need Recipe Item Sync and at least one supported recipe viewer. Custom textures, models, and translations still require the datapack author's resource pack on the client.

Overview

Datapacks often create custom items by using vanilla ItemStacks with components, CustomModelData, custom names, lore, loot tables, commands, or custom crafting systems. Those items may work perfectly in-game while remaining invisible to normal recipe viewers.

Recipe Item Sync v3 bridges that gap. It can synchronize:

  • ItemStack outputs accepted by Minecraft's RecipeManager.
  • Names, lore, CustomModelData, custom data, data components, and stack counts.
  • Supported fallback crafting displays for datapack crafting JSON.
  • Deterministic virtual item definitions from supported item loot tables.
  • Supported static datapack item-entity crafting systems with deterministic outputs.

Installation

  1. Server Install the matching Recipe Item Sync v3 JAR in the server's mods folder.
  2. Client Install the same Recipe Item Sync target and at least one supported viewer: JEI, REI, or EMI where available.
  3. Datapack Keep the datapack on the server as usual. No client-side copy is required for synchronization.
  4. Resource pack If the custom items use custom textures, models, or translations, make sure the matching resource pack is available to clients.
  5. Join the server Recipe Item Sync builds a server snapshot and sends supported virtual content to the client.

How it works

1

Collect

The server inspects supported recipes, virtual ItemStacks, deterministic item loot tables, and supported custom crafting data.

2

Snapshot

The discovered content is normalized into a deterministic snapshot with stable virtual identifiers.

3

Sync

The server sends the snapshot to connected clients running Recipe Item Sync.

4

Display

The client applies the supported content through the installed recipe viewer's public integration APIs.

Automatically discovered items use stable ris: virtual IDs derived from their source. Manually configured entries keep the virtual ID written in the configuration.

Configuration

The current v3 configuration file is: config/recipeitemsync/recipeitemsync.json

If the new file does not exist and an older config/recipeitemsync/server/recipeitemsync.json is present, v3 migrates the legacy file automatically. 

{
  "viewerPreference": "auto",
  "namespaces": [],
  "manualVirtualItems": []
}

viewerPreference

Controls which installed recipe viewer receives Recipe Item Sync content.

ValueBehavior
autoAutomatically synchronizes supported installed viewers.
allAllows all supported installed viewers.
jeiLimits Recipe Item Sync integration to JEI.
reiLimits Recipe Item Sync integration to REI.
emiLimits integration to EMI where EMI is supported for that Minecraft target.

Invalid or blank values fall back to auto.

namespaces

Optional allow-list for virtual content namespaces. An empty list allows all eligible namespaces. This is useful when a modpack only wants Recipe Item Sync to expose content from selected datapacks. 

{
  "viewerPreference": "auto",
  "namespaces": [
    "stellarity",
    "my_datapack"
  ],
  "manualVirtualItems": []
}

Entries ending with :* are also accepted, for example stellarity:*.

Manual virtual items

Automatic discovery should be preferred. Manual entries exist as a fallback for items that cannot be discovered safely from normal recipe or deterministic datapack data. 

{
  "viewerPreference": "auto",
  "namespaces": [],
  "manualVirtualItems": [
    {
      "virtualId": "my_pack:ancient_relic",
      "hostItem": "minecraft:paper",
      "customModelData": 1001,
      "displayName": "Ancient Relic",
      "tooltip": [
        "A manually exposed datapack item"
      ]
    }
  ]
}
FieldPurpose
virtualIdUnique identifier used by Recipe Item Sync.
hostItemThe vanilla or modded base item used to build the displayed ItemStack.
customModelDataOptional positive CustomModelData value.
displayNameOptional display name hint.
tooltipOptional list of tooltip lines.

Commands

Recipe Item Sync's administration commands require Minecraft permission level 2.

/recipeitemsync statusShows the current synchronization state and snapshot diagnostics.
/recipeitemsync clientstatusShows Recipe Item Sync synchronization diagnostics.
/recipeitemsync resync <player>Rebuilds the snapshot and schedules a fresh sync for the selected player or players.
/recipeitemsync resync allRebuilds the snapshot and schedules a fresh sync for everyone online.
/recipeitemsync dumpWrites a diagnostic snapshot report under recipeitemsync-dumps.
/recipeitemsync give <virtualId>Gives the resolved virtual ItemStack to the command player. Virtual IDs are suggested by the command.

Recipe viewer support

JEI

Receives runtime virtual item entries and supported dedicated datapack recipe displays.

REI

Receives discovered virtual item entries. Dedicated custom datapack crafting categories may be more limited than JEI.

EMI

Supported on Minecraft 1.21.1. Recipe application follows EMI's reload lifecycle rather than mutating frozen EMI internals.

For datapack authors

Recipe Item Sync works best when a custom item has a deterministic ItemStack that can be derived from recipe or loot-table data. You normally do not need to maintain a separate client-side list.

Best results

  • Use stable recipe and loot-table identifiers.
  • Keep output ItemStacks deterministic when possible.
  • Use normal data components for names, lore, CustomModelData, and custom data.
  • Provide a resource pack separately when custom visual assets or translations are required.

Custom systems

Static item-entity crafting systems can be exposed when their required inputs and deterministic outputs can be represented safely. Arbitrary mcfunction logic cannot always be converted into a recipe viewer display.

Troubleshooting

The item does not appear

  1. Confirm that the server and client use the matching Recipe Item Sync target.
  2. Confirm that the client has a supported recipe viewer installed.
  3. Run /recipeitemsync status and check whether the expected virtual content is present.
  4. Run /recipeitemsync dump and inspect the generated diagnostic report.
  5. Check whether namespaces is filtering out the datapack namespace.
  6. Run /recipeitemsync resync all after changing datapack content or configuration.
  7. Check server and client logs for Recipe Item Sync or viewer integration messages.

The item appears but has the wrong texture

Recipe Item Sync synchronizes ItemStacks and recipe metadata, not resource-pack assets. The client still needs the resource pack that contains the custom texture or model.

The datapack uses commands or functions

Command-driven systems are supported only when Recipe Item Sync can determine a stable input and output representation. If the result depends on dynamic mcfunction logic, random state, scoreboards, or other runtime conditions, a safe recipe display may not be possible.

After /reload

Recipe Item Sync is designed to rebuild and resynchronize supported datapack content without leaving old duplicate virtual entries. If a viewer does not refresh as expected, use /recipeitemsync resync all and inspect the dump and logs.

Known limitations

  • Recipe Item Sync does not register datapack items as normal registry items.
  • It does not distribute textures, models, fonts, translations, or other resource-pack files.
  • Highly custom modded recipe types can expose an output while still being impossible to display as a normal recipe.
  • Arbitrary mcfunction systems are only shown when their inputs and outputs can be represented safely and deterministically.
  • Dedicated custom recipe categories are not identical across JEI, REI, and EMI.

FAQ

Does the datapack need to be installed on every client?

No. The datapack can remain server-side. Clients need Recipe Item Sync and a supported recipe viewer.

Do clients still need the resource pack?

Yes, if the datapack relies on custom textures, models, fonts, or translations.

Does Recipe Item Sync create real registered items?

No. It synchronizes virtual ItemStacks and recipe metadata for supported recipe viewers.

Can it show altar or item-entity recipes?

Yes, when Recipe Item Sync can statically determine the required item inputs and deterministic output.

What should I send with a bug report?

Include the Minecraft version, NeoForge version, Recipe Item Sync version, recipe viewer and version, server/client logs, and ideally the output from /recipeitemsync dump.
